# BMWcodes V10 — проверка проекта

Дата: 5 октября 2026. Проверена локальная версия исходников и production-сборка. Исправления включены в этот архив. Hero, About и их изображения не изменены.

## Итог

Локальная сборка и перечисленные ниже функциональные проверки проходят. Готовность работающего публичного сервиса ещё не подтверждена: доступа к развёрнутым Vercel/Railway/Supabase в этой проверке не было. Это аудит кода и локальных сценариев, не сертификация безопасности и не полноценный внешний пентест.

## Что проверено

- Production-сборка Next.js 15.5.27: успешно, все страницы сгенерированы. Для теста использован непубличный адрес-заглушка https://audit-api.example/api/bookings, в исходниках и архиве он не является настройкой запуска.
- TypeScript: npm run typecheck без ошибок.
- .NET 10: Release publish успешен. Проверка NuGet, включая транзитивные зависимости, не нашла известных уязвимых пакетов на момент запуска.
- Chromium: главная на ширинах 390/768/1440/1920; booking/services/admin/privacy на 390/768/1440. Страницы открываются, горизонтального переполнения нет, необработанных pageerror нет. Просмотрены снимки формы; календарь помещается в экран, Escape закрывает его, кнопка отправки видна. Анимация фар выключается кнопкой и при reduced motion.
- Компонентные проверки: дата New York около полуночи, конец месяца и високосный год; границы календаря; двойная отправка даёт один fetch; корректный payload; loading и success state.
- Интеграционные проверки API с локальным PGlite через PostgreSQL-протокол: повторное применение SQL, отказ anon в чтении; health; 401 без токена и с подделанным токеном; успешный вход; валидация даты; сохранение 5 заявок с ID и 429 на шестую; Retry-After; авторизованный список; разрешённый и запрещённый CORS origin.
- Подставленные X-Real-IP/X-Forwarded-For при отсутствии доверенного прокси не обходят лимит. Явно доверенный тестовый loopback-прокси обрабатывается.
- 12 одновременных неверных входов: ровно 5 ответов 401 и 7 ответов 429. Ответы входа имеют no-store. Тело более 16 КБ получает 413.
- Перезапуск API сохраняет записи и лимит заявок при продолжающей работать тестовой БД. Импорт camelCase/PascalCase JSONL; повтор того же файла не создаёт дублей; повреждённая строка откатывает импорт целиком.
- Недоступная таблица приводит к безопасному 503 без деталей Npgsql в ответе.
- Проверена конфигурация production build: отсутствующий URL, HTTP, неверный путь и credentials внутри URL отклоняются.

PGlite — локальная тестовая реализация PostgreSQL. Это не проверка настоящего Supabase, его TLS/pooler, восстановления после сбоя БД или advisory-lock конкурентности нескольких PostgreSQL-сессий.

## Остаётся до публичного запуска

1. **Privacy пустая.** /privacy содержит только заголовок. Нужен согласованный владельцем текст: кто обрабатывает данные, цели, поставщики, срок хранения, контакт для запросов и фактические правила удаления. Эти решения не выдуманы при аудите.
2. **Доверенный прокси Railway.** Указать подтверждённые ingress IP/сети и используемый заголовок. Без этого лимит безопасно использует socket peer, но посетители одного прокси могут делить один лимит. Нельзя включать доверие всему Интернету. Проверить подмену заголовков извне после деплоя.
3. **Настройки окружений.** Vercel: реальный NEXT_PUBLIC_BOOKING_API_URL до сборки. Railway: секреты и точные ALLOWED_ORIGINS. Supabase: SQL-схема, рабочая строка подключения и SSL Mode=VerifyFull. Реальных секретов в архив добавлять не нужно.
4. **Резервные копии.** PostgreSQL не означает автоматическую защиту от удаления данных. Настроить резервирование и проверить восстановление в отдельную БД. В рамках этого аудита восстановление backup не выполнялось.
5. **Контрольный запрос после деплоя.** Отправить тестовую заявку с сайта, проверить её в админке, перезапустить backend и проверить сохранность. Проверить неверный origin, rate limit и сообщения при недоступности API.

## Оставшиеся ограничения и дальнейшие улучшения

- Лимит входа в админку локален для процесса, сбрасывается перезапуском и не общий для реплик. Для нескольких реплик нужен общий счётчик или ограничения на ingress; локальный тест гонки этого не решает.
- Токен админки хранится в sessionStorage, действует до 12 часов. Logout очищает браузер, но не отзывает уже украденный токен. MFA и серверный отзыв не реализованы. Для усиления защиты нужны отдельные решения по аутентификации.
- Нет ключа идемпотентности booking: если БД сохранила заявку, а ответ потерялся, ручной повтор может создать дубль. Защита от двойного клика не покрывает потерю ответа.
- Админка показывает последние 500 заявок, без пагинации и автоматического обновления; это не полный архив. Для свежих данных можно перезагрузить страницу.
- Подключение ролью postgres имеет широкие права. RLS/REVOKE закрывают anon/authenticated, но не защищают от утечки owner-пароля. Отдельная роль backend с минимальными правами — рекомендуемое усиление перед эксплуатацией.
- CORS ограничивает браузеры, но не мешает прямым запросам к API. Лимит по IP не заменяет защиту от распределённого спама. CAPTCHA не добавлялась.
- Нет автоматического срока удаления заявок/IP-хешей. Политику хранения должен определить владелец.
- Не выполнялись нагрузочное тестирование, Safari/Firefox, полноценный screen-reader аудит и проверка доставки уведомлений. Заявки доступны через админку; email/SMS-уведомления не реализованы.
- CSS содержит накопленные переопределения. Проверенные размеры работают; рефакторинг дизайна не выполнялся.

## Повторяемые команды

Frontend (Node.js 22.12+ или 24):

```sh
npm ci
npm audit
npm run typecheck
# Установить настоящий NEXT_PUBLIC_BOOKING_API_URL в окружении перед следующей командой.
npm run build
```

Backend (.NET SDK 10):

```sh
dotnet restore backend/BmwCodes.BookingApi.csproj
dotnet list backend/BmwCodes.BookingApi.csproj package --vulnerable --include-transitive
dotnet publish backend/BmwCodes.BookingApi.csproj -c Release
```

Подробная настройка сервисов: DEPLOY_RU.md. Dev-режим npm run dev сохраняет локальный API http://localhost:5080/api/bookings. Production-сборка требует настоящий HTTPS API.
